## 1. Import design
Import the synthesis netlist, LEF files, mmmc file.

### synthesis netlist
the gate-level netlist generated by design compiler.

### LEF files
abstract physical libraries used by Innovus for placement and routing. They describe cell and macro geometry (width/height, site), pin locations, blockages, and routing layers/via rules (from tech LEF and macro LEF), but do not contain timing or power information.

- **Macro LEF** (e.g., `gsclib045_macro.lef`):  
  Abstract view for standard cells and macros for APR.  
  It provides:
  - Cell geometry  
  - Pin position  
  - Blockage  
  - Placement unit tile  
  - DRC rules  

- **Tech LEF** (e.g., `gsclib045_tech.lef`):  
  Abstract view for metals and vias for routing.  
  It provides:
  - Current density  
  - Spacing rules  
  - Other routing-related technology rules

### MMMC files
multi-mode multi-corner (MMMC) setup files used to define timing analysis environments.

- **Timing constraints**:  
  Timing constraints tell the tool **how fast the circuit is supposed to run** and **how signals interact with the outside world**.  
  They are usually written in an SDC file and include:
  - Clock definitions (period, waveform, uncertainty, etc.)  
  - Input arrival times and output required times (input/output delays)  
  - Special path exceptions, such as false paths and multicycle paths  
  With these constraints, the tool knows what timing requirements it must satisfy between registers and between the chip and its environment.

- **Mode (constraint mode)**:  
  
In this lab, the `mmmc.view` file does the following:

- **RC corner**:  
  It creates one RC corner named `RC` using the QRC tech file `gpdk045.tch`.  
  This tells the tool how to model wire resistance and capacitance for extraction.

- **Library sets (max / min)**:  
  It creates two library sets:
  - `lib_max`: uses `slow_vdd1v2_basicCells.lib` (slow cells) and `slow.cdb` (SI library)  
    → used for the **max-delay** case (worst delay, for setup checks).  
  - `lib_min`: uses `fast_vdd1v2_basicCells.lib` (fast cells) and `fast.cdb`  
    → used for the **min-delay** case (best delay, for hold checks).

- **Timing constraints and constraint mode**:  
  Timing constraints tell the tool how fast the circuit should run and how it interacts with the external world.  
  They are written in an SDC file and include:
  - Clock period and waveform  
  - Input/output delays  
  - Path exceptions (false paths, multicycle paths), etc.  

  The file creates one **constraint mode**:
  - `CN_func`: functional mode, using `../pre_layout/top_pipe_syn.sdc` as its SDC file.  
    This single SDC describes the timing constraints for normal operation.

- **Delay corners**:  
  It combines each library set with the RC corner `RC` to form delay corners:
  - `DC_max` = (`lib_max`, `RC`) → worst delay corner for setup  
  - `DC_min` = (`lib_min`, `RC`) → best delay corner for hold  

In static timing analysis, the delay of a timing path is modeled as the sum of **cell delay** and **wire delay**.  
The **cell delay** is taken from the timing library (liberty file) and depends on the input slew and output load of each standard cell.  
The **wire delay** is obtained from RC extraction using the RC corner (e.g., `gpdk045.tch`), which provides resistance and capacitance models for each metal and via layer.  
Under MMMC, different delay corners (such as `DC_max` with slow cells and `DC_min` with fast cells, both using the same RC corner) are combined with the same timing constraints (SDC) in different analysis views, so the tool can check both worst-case setup timing and worst-case hold timing on the same design.
  

- **Analysis views**:  
  One analysis view = one constraint mode + one delay corner.  
  The file defines:
  - `AV_max` = (`CN_func`, `DC_max`) → functional mode @ max corner (for setup)  
  - `AV_min` = (`CN_func`, `DC_min`) → functional mode @ min corner (for hold)


## 2. Modify IO constraint file

### What is the I/O file?

The I/O constraint file (`.io`) tells Innovus where to place each top-level pin around the core.

The file has an `iopin` section with four side blocks:

- `(top …)`
- `(left …)`
- `(bottom …)`
- `(right …)`

Inside each side block there are pin lines, for example:

```
(pin name="clk" layer=2 width=0.0800 depth=0.2500 place_status=placed)
```

For a file saved with `saveIoFile -byOrder`:

- The side name (`top` / `left` / `bottom` / `right`) decides on which edge the pin is placed.
- The order of pin lines inside each side block decides the physical order along that edge:  
  – `top` / `bottom`: from left to right  
  – `left` / `right`: from bottom to top  

Innovus then distributes the pins evenly along each side according to this order (no explicit x/y coordinates are written in this format).

---

### Why do we modify the I/O file?

The auto-generated I/O file only follows the **netlist port declaration order**.  
It does not know:

- which signals are special (clock, reset), or  
- which pins belong together (buses, memory / peripheral interfaces).

If we keep the default I/O file, we may get:

- Clock and reset pins placed near a **corner**, which makes the clock tree root unbalanced and increases skew.
- Bits of the same bus (for example `boot_addr[7:0]`, `boot_datai[31:0]`, `peri_addr[15:0]`, `peri_datao[15:0]`) scattered or interleaved with unrelated pins, causing longer routes, more crossings, higher congestion, and worse timing.
- Very uneven numbers of pins on each side, so one edge becomes much more congested than the others.

In Lab11 we modify the I/O file in order to:

- Place `clk` and `rst_n` roughly in the **middle of one side** (e.g., the top edge), so the clock tree is easier to balance and the clock insertion is more symmetric.
- Group related signals together (address/data buses and peripheral interface signals), so routing is more regular and shorter.
- Keep the I/O distribution over the four sides more reasonable to avoid local hot spots of congestion.


## Set process node

Command in Innovus:

setDesignMode -process 45

This command tells Innovus that the design is implemented in a 45 nm technology node (GPDK45 in this lab).  
The detailed routing and DRC rules still come from the technology LEF, but the process setting helps the tool choose appropriate internal defaults (for example, for congestion estimation and some technology-dependent heuristics).

## Power/Ground connection (Connect Global Nets)

Menu path:

Power -> Connect Global Nets...

In the synthesized netlist, the VDD and VSS pins of standard cells are usually not connected by explicit Verilog nets.  
The “Connect Global Nets” step tells Innovus:

- which net name should be treated as the global power net (VDD), and  
- which net name should be treated as the global ground net (VSS),

and then logically connects all cell power pins that match these names to the corresponding global nets.

At this point, the connection is **logical** (inside the database), not physically routed yet.  
This is required before building the power structure and before doing meaningful timing / IR / routing analysis.


## Floor plane 
The floorplan step is where we turn a purely logical design (netlist + timing) into a physical layout outline:

- decide the **die** size and shape,
- define the **core area** where standard cells are allowed to be placed,
- leave margins between the core and the IO ring,
- reserve space for **power rings** (VDD/VSS) around the core.

In Innovus (Floorplan -> Specify Floorplan...), we mainly set:

- **Core area / aspect ratio**:  
  This defines the rectangular region where standard cells will live.  
  If the core is too skinny or too small, routing will be harder and congestion will increase.

- **Core utilization**:  
  Roughly = (total standard cell area) / (core area).  
  A higher utilization means a smaller and denser core (better area), but also less whitespace for routing and buffering, which can lead to congestion and timing problems.  
  In this lab we use a relatively low utilization so that placement and routing are easier and faster for a teaching example.

- **Core to IO boundary (core margin)**:  
  This is the distance between the core edge and the IO boundary.  
  We choose this margin large enough to:
  - place multiple VDD/VSS power rings around the core, and  
  - keep standard cells away from the IO pins.  

  Conceptually, this margin must cover:  
  “inner spacing from core to first ring + all power ring widths + spacing between rings + spacing to IO pins”.  
  The exact numbers in the lab are chosen so that all planned rings and spacings fit exactly into this margin.


## Initial Placement

After floorplan and an initial placement in “floorplan mode”, we run:

1. place_design  
2. refinePlace -checkRoute 1  
3. Early global route  
4. Report timing  

This gives a **rough placement and simple routing** that is only used to quickly estimate timing and congestion, not as the final implementation.

## Analyze congestion

Menu path:

Route -> NanoRoute -> Analyze Congestion

The tool divides the core area into global routing cells (gcells) and estimates:

overflow = (number of nets that need to pass through a gcell) – (available routing tracks in that gcell)

The congestion map uses color to show how severe the overflow is:

- low / zero overflow → light colors (easier routing),  
- high overflow → red regions (difficult routing, potential DRC and timing problems).

In this lab, we use this step to **visualize whether the current floorplan and IO placement create any obviously congested regions**.

**Step 6 – Unplace standard cells and delete signal routing**

Commands in Innovus:

unplaceAllInsts  
editDelete -type Signal

These two commands **clean up** the temporary placement and routing:

- `unplaceAllInsts`:  
  removes the placement of all standard cells and returns to a state where the core has floorplan and IOs, but no cells placed.

- `editDelete -type Signal`:  
  deletes all **signal routing** created by early global route or trial routing,  
  while keeping power structures (power ring / power nets) intact.

The important point is that the initial placement and routing we just performed are **only for demo and analysis** (timing preview and congestion check).  
They are low-effort, floorplan-mode results and are **not** intended to be reused as the final implementation.  
Therefore, after observing the congestion map, we clean the layout so that later labs can start from a clean floorplan and run formal placement and routing with the proper flow.

**Step 7 – Save design (clean floorplan checkpoint)**

Menu path:

File -> Save Design...

After removing the temporary placement and signal routing, we save the design again.  
This checkpoint now contains:

- floorplan and IO placement,  
- power/ground connections and any power structures built so far,  
- MMMC and timing constraints,

but **no standard cell placement and no signal routing**.

This “clean floorplan + power” checkpoint will be used as the starting point for the formal placement, CTS, and detailed routing in later stages of the APR flow.
